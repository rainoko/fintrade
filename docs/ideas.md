## Performance: ticker detail view is slow to load charts

Root cause (verified in code, not speculation): `GET /api/stocks/{ticker}/indicators` — which feeds every chart pane on the stock detail page — calls `app.signals.engine.analyse_history()`, which re-runs the *entire* Triple Screen pipeline (`analyse()`: Tide, Wave, Trigger, confidence scoring, divergence/kangaroo-tail lookups, full Pydantic model construction) once per daily bar in the requested range. `range=1y` is ~252 iterations; `range=max` on a ticker with years of history is thousands. Most of the expensive per-indicator series ARE precomputed-and-sliced (not recomputed) already — the residual cost is per-bar Python/pandas call overhead (confidence scoring, dict/slice construction, model construction) repeated thousands of times, plus a synchronous, sequential `get_daily_ohlcv()` → `get_weekly_ohlcv()` provider fetch with only a 24h cache TTL (cold-cache first load pays real yfinance network latency on top).

Candidate fixes, roughly ordered by leverage-to-effort:

- **Cache the computed `IndicatorHistoryResponse` itself**, analogous to the existing `ohlcv_cache`/`extended_data_cache` tables. The whole thing is a pure function of `daily_ohlcv`/`weekly_ohlcv` as of "today" — it doesn't change intraday, so a `(ticker, range)`-keyed cache with a same-day TTL would make every request after the first same-day one instant. Probably the single highest-leverage fix for the least risk, since it doesn't touch the computation itself.
- **Vectorize the per-bar loop** where the math genuinely allows it (e.g. signal/confidence determination is a mostly-deterministic function of the already-precomputed series — could plausibly run as pandas/numpy operations across the whole series instead of a Python `for i in range(...)` calling `analyse()` per bar). Bigger rewrite, real risk of behavior drift, needs the same `verify-elder-signal` scrutiny as any signal-engine change — but addresses the root architectural cost directly rather than caching around it.
- **Fetch daily + weekly OHLCV concurrently** instead of sequentially (`backend/app/api/routers/stocks.py`'s `get_indicator_history` currently does `daily_ohlcv = provider.get_daily_ohlcv(...)` then `weekly_ohlcv = provider.get_weekly_ohlcv(...)` one after another). Small, low-risk win specifically for cold-cache loads.
- **Reconsider the 24h OHLCV cache TTL** — daily bars only close once per trading day, so the freshness requirement may tolerate a longer TTL (or a "cache until next market close" policy) without any staleness cost, reducing how often the expensive cold-cache path is hit at all.
- Lower priority / needs more thought: downsampling very long `range=max` responses (do chart panes actually need daily-granularity points for a 10-year view, or would every-Nth-bar suffice above some threshold?) — real payload/render-cost win but changes what the frontend can show, needs a product decision, not just an engineering one.

## Surface suggested stop-loss/profit-target more prominently for open positions

The backend already computes both (`app.portfolio.risk.protective_stop`/`stop_from_price_action`, `app.portfolio.profit_target.suggest_profit_target`), but they're not visible where a user would naturally look:

- **Portfolio list** (`PositionsTable.tsx`, the actual positions table on `PortfolioPage`) has no `protective_stop`/`profit_target` columns at all — both only exist in the separate `RiskPanel` section further down the same page. So the primary "what do I own" view gives no at-a-glance stop/target, you have to scroll to a second table and re-find the row.
- **Stock detail page** (`StockDetailPage.tsx`) has zero position-awareness — viewing a ticker you actually hold shows the same generic signal/analysis as viewing any other ticker, with no "you're in this at $X, your stop is $Y" context, even though the position data and `protective_stop` formula are both available.

Real constraint to think through before scoping this: `suggest_profit_target` is currently BUY-only (only computed for a *fresh* BUY signal, per `backend-profit-target`'s own decisions) — an already-held position whose signal has since drifted to HOLD/SELL wouldn't have one under the current formula. Whether "suggested profit target for an open position" should keep that BUY-only gate or compute a target off the position's actual entry regardless of today's signal is a real methodology question, not just a wiring exercise — worth an explicit decision (and maybe an `elder-signal-reviewer` look) rather than assuming either way.

**Grounded in the book now** (read ch. 53 "How to Set Profit Targets" and ch. 54 "How to Set Stops" directly, *The New Trading for a Living* 2014, pp. 217–225):

- Ch. 53 doesn't gate profit targets to entry day only — a target set at entry (via moving averages/value zone for swing trades, channel lines, or nearest support/resistance for position trades) is meant to be tracked for the life of the trade, not recomputed only while the signal happens to say BUY. This leans toward *not* keeping the BUY-only gate for an already-open position's displayed target — worth revisiting `backend-profit-target`'s decision now that the actual primary-source text is in hand, not just inferred.
- Ch. 54 has a whole subsection, **"Don't Let a Winning Trade Turn into a Loss,"** that the app doesn't implement at all yet: as unrealized profit grows, move the stop to breakeven ("cuffing the trade") once profit crosses some threshold, then keep ratcheting the stop up to protect a growing fraction (Elder's own example: a third) of open profit as it increases. This is a distinct, genuinely new feature from the existing static SafeZone `protective_stop` — a **trailing/profit-protecting stop** that reacts to how far a position has moved in its favor, not just current volatility.
- Companion principle from the same chapter, **"Move Your Stop Only in the Direction of Your Trade"** — a stop should never be loosened once set, only tightened. Any trailing-stop feature needs to enforce this as a hard ratchet (ancestor-of-max(previous suggested stop, new SafeZone stop) for a long), not just report whatever `protective_stop` computes fresh each time, or it'd contradict the exact discipline this idea is trying to encode.
- Also mentioned, not yet implemented, lower priority: **ATR-based stops** (Kerry Lovvorn's "place stop >=1 ATR — 2 ATR is safer — from the entry bar's extreme," usable as a trailing stop too) — worth noting since ATR is already computed by this app (`backend-indicator-atr-adx`), so this is a cheap alternative/companion to SafeZone if it's ever worth offering a second stop method. **Nic's stop** (second-lowest-low/second-highest-high instead of the literal extreme, to avoid the crowd's obvious stop-running level) and **catastrophic/GTC hard stops** as a backstop under a soft/adaptive stop are both mentioned in the same chapter but feel more like "considered, not built" entries for the methodology page than something to build now.
- **Correction from reading ch. 39 "Triple Screen Trading System" directly** (p. 161, "Stops and Profit Targets" section): *"Triple Screen calls for setting profit targets using long-term charts and stops on the charts of your intermediate timeframe... When buying a dip on a daily chart, the value zone on a weekly chart presents a good target."* This app's intermediate timeframe is daily (Wave/Screen 2) and long-term is weekly (Tide/Screen 1) — but `suggest_profit_target`'s channel/support-resistance target and `protective_stop`'s SafeZone stop are **both computed entirely off daily data**. Per this explicit rule, the profit target should be drawn from the *weekly* chart's channel/value-zone, not the daily one — the stop staying on daily is already correct. Worth an `elder-signal-reviewer`-style pass on `backend-profit-target` specifically checking this against the primary source, since it may be a real methodology gap, not just a nice-to-have refinement.

## Switchable trading mode (position/swing trader vs. day trader) — different Triple Screen timeframe scales

Grounded directly in ch. 39, "Choosing Timeframes—the Factor of Five" (pp. 155–162): Triple Screen doesn't hard-code weekly/daily/intraday — it's built around *whatever three timeframes the trader picks*, each related to its neighbor by roughly a factor of five. You choose your preferred ("intermediate") timeframe; the long-term (Tide) chart is one order of magnitude longer, the short-term (entry/Trigger) chart one order of magnitude shorter. This app currently hard-codes the swing/position-trader pairing (weekly = long-term/Tide, daily = intermediate/Wave, same-day-or-shorter = Trigger) — which is exactly one specific choice on this scale, not the only one Elder describes.

The book gives day-trading as the other explicit example: *"Day traders who hold their positions for less than an hour... a 5-minute chart may define the intermediate timeframe, a 25-minute chart the long-term timeframe, and a 2-minute chart the short-term timeframe."* Also offered: a 39-minute/8-minute pairing, chosen specifically because 39 minutes divides the 390-minute US trading day into a clean 10 bars.

If this were ever built as a real "mode" toggle (not just a documentation note), the real implications:

- **Needs intraday OHLCV data the app doesn't fetch today** — `DataProvider` only exposes `get_daily_ohlcv`/`get_weekly_ohlcv`. yfinance's intraday granularity is available but has a short lookback window (a real limitation, not just a wiring gap). The already-built optional `IBKRProvider` (`backend/app/data/ibkr_provider.py`) is the most plausible near-term source — checked its actual current state before assuming it's ready:
  - It already talks to `GET /iserver/marketdata/history`, the right endpoint, but `get_hourly_bars()` hardcodes `_BAR_INTERVAL = "1h"` — only hourly bars are implemented today, not the 5-min/25-min/2-min (or 39-min/8-min) granularities ch. 39's day-trading example actually calls for. Worth checking what `bar` values IBKR's endpoint genuinely accepts before assuming this needs new endpoint research versus just parameterizing the existing call.
  - It takes an IBKR **conid (contract id)**, not a ticker symbol — there's no symbol→conid resolution built (the task's own decisions explicitly deferred this, noting `/iserver/secdef/search` wasn't researched as part of that task). A day-trader-mode feature can't just pass in "AAPL"; conid resolution is a real, separate piece of work.
  - It's deliberately **not** part of the `DataProvider` interface and **not wired into any route today** — both by explicit design decision (kept it out of the interchangeable-provider contract since it's not a drop-in for yfinance/Stooq). So beyond the granularity/conid gaps, there's no existing consumer to extend — this would be new plumbing from scratch, not a config flip.
  - It's optional and disabled by default, requiring a real interactive browser login to a locally-run gateway process the user must set up themselves — so even once built, day-trader mode backed by IBKR would only work for users who've done that setup, not as a universal default the way daily/weekly data is today via yfinance.
- Signal engine functions (`evaluate_tide`/`evaluate_wave`/`evaluate_impulse`) are already timeframe-agnostic in the sense that they just take an `ohlcv` DataFrame — so the *math* mostly generalizes. The hard part is everywhere the app currently assumes "weekly" and "daily" as fixed concepts (schema field names like `weekly_macd_histogram_slope`, the `_weekly_through_bar_date` calendar-week truncation logic, cache tables keyed by `interval: 'daily'|'weekly'` only) rather than a generic long-term/intermediate/short-term triple.
- This is a genuinely large feature (new data source + a real architecture change to how "timeframe" is modeled, not just a UI toggle) — feels like the kind of thing worth its own design pass before scoping into tasks, not a quick followup.

### Ties back to the caching idea above

If day-trader mode ever ships, it makes the `IndicatorHistoryResponse` caching idea *more* urgent, not less — running the same per-bar `analyse()` loop over minute/5-minute bars for a trading day multiplies the iteration count well past what daily-bar `range=max` already costs, and the cache key would need to include the timeframe-mode (not just ticker+range) once more than one mode exists. Worth keeping in mind when scoping the caching work: design the cache key to be mode-aware from the start rather than needing a migration later.

## IBKR Client Portal Gateway is now live and authenticated — concrete next steps

Verified live in this session (not just documented): the gateway answers authenticated at `https://localhost:5000/v1/api/iserver/auth/status` (`{"authenticated":true,"established":true,"connected":true,...}`), and `FINTRADE_IBKR_ENABLED=true` is now set in `backend/.env`. `IBKRProvider` (`app/data/ibkr_provider.py`) itself is completely untouched by this — every one of its tests mocks the `_request` boundary (its own module docstring says so explicitly), and `backend-ibkr-data-provider`'s `decisions` entry records live-gateway behavior as "deferred to manual testing by the user against a real running gateway." That gap is closable now, but hasn't been closed yet — this session deliberately didn't exercise `IBKRProvider` itself, only the raw gateway endpoint directly via `curl`.

Real gaps blocking actual use, roughly in dependency order:

- **No route consumes `get_ibkr_provider` at all.** `app.api.dependencies.get_ibkr_provider` exists and is even a properly thread-safe singleton now (`backend-ibkr-data-provider-followups`), but nothing calls it — the provider is fully dormant end-to-end. The smallest useful next step is a read-only status endpoint (e.g. `GET /api/ibkr/status` wrapping `get_gateway_status()`) so the app can actually surface "IBKR: connected / not authenticated / gateway down" instead of this being invisible everywhere.
- **No `/tickle` keep-alive anywhere in the codebase.** `docs/architecture/Backend.md` §8 documents the requirement ("keep the session alive with a periodic `GET /tickle` call roughly once a minute") as a manual step for whoever does the browser login — but nothing in `IBKRProvider` or the FastAPI app itself ever calls it. Without this, tonight's manual login will silently expire on its own (IBKR's session timeout is short), and `get_gateway_status()` will start reporting `not_authenticated` the next time anything checks — not a bug, just an unimplemented requirement. Needs a background repeating task (FastAPI lifespan/startup job) calling `/tickle`, gated behind `ibkr_enabled` like every other IBKR code path.
- **No symbol→conid resolution.** `get_hourly_bars`/`run_scanner` both key off IBKR's own numeric `conid`, not a ticker symbol — there's no `/iserver/secdef/search` (or `/trsrv/stocks`) wrapper anywhere, and `backend-ibkr-data-provider`'s own `decisions` entry explicitly deferred researching it. Any real consumer (a route taking `?ticker=AAPL`, matching how every other endpoint in this API works) needs this solved first — genuinely new research/work, not just wiring an existing piece in.
- **Bar interval hardcoded to `1h`.** Already flagged under "Switchable trading mode" above as the specific thing blocking day-trader-mode's finer intervals (5-min/39-min/etc.) — noted here too since it's the same provider and now testable against a real gateway instead of only mocks.
- **A real market-breadth signal, not just the personal-watchlist proxy.** `backend-watchlist-breadth-proxy` (done) only aggregates Tide direction across the *user's own* tracked tickers — a genuine NH-NL/advance-decline breadth reading needs a broad market universe this app doesn't otherwise have. `IBKRProvider.run_scanner`'s 52-week-high/low scan types (confirmed present in `get_scanner_params`'s option list) are exactly the mechanism `docs/architecture/Backend.md` names for this ("IBKR market scanner (broad-market-breadth detection)"), but it's never been run against a live gateway or wired to anything. Once the pieces above exist, this is the actual payoff feature the IBKR integration was originally for, beyond hourly bars.
- **A live-gateway verification pass on `IBKRProvider` itself.** Now that a real authenticated session exists, it's worth actually calling `get_gateway_status()` / `get_scanner_params()` / a small `get_hourly_bars()` through the real class (not just raw `curl` against the gateway) to catch any response-shape surprises the mocked tests wouldn't — e.g. confirming `/iserver/scanner/params`'s real payload matches what `_parse_bars`/`_parse_scanner_results` assume. Deliberately not done in this session (asked not to test it yet) — this is the natural first real step whenever someone does pick this up.

## No manual "Sell / Close position" form — only a bare confirm-delete dialog

Not about live order execution (explicitly out of scope for now — not ready for that) — this is about the existing manual-entry-only workflow being lopsided. "Buy" (adding a position) already has a real form: `AddPositionDialog.tsx` (ticker, quantity, avg cost basis, entry date) behind `useAddPosition` / `POST /api/portfolio/positions`. "Sell" has no equivalent — verified in code, `PositionsTable.tsx`'s close flow is a bare `ConfirmDialog` ("Delete AAPL (10 shares)? This cannot be undone.") wired to `useDeletePosition`, whose mutation signature is just `(id: string)` — zero user-editable fields — calling `DELETE /api/portfolio/positions/{id}`.

That produces two distinct, separately-worth-fixing gaps:

- **`exit_reason` is never actually chosen by the user.** The backend endpoint already accepts an `exit_reason` query param (Elder's own taxonomy — profit target hit, stop hit, signal reversal, etc., `docs/Analyse.md` §7) feeding `backend-trade-grading` and the trade journal, but no UI ever surfaces that choice — every position closed from the app today silently records `exit_reason=unspecified` regardless of the real reason. The trade-journal/grading feature already exists and works; it's just being fed a placeholder on this one field. Cheapest fix of the two: add a reason `<select>` to a real close-position dialog, matching the taxonomy `ExitReason` already defines.
- **`exit_price`/`exit_date` are hard-locked to "today, at today's live market close."** This is a deliberate, already-made design decision (`backend-trade-history-table`'s `decisions` entry: "this app already treats 'current market price' as authoritative... not trusting a client-supplied number"), reasonable for the common case of closing a position you're selling *right now*. But it means there's no way to backfill a trade that already fully happened in the past — e.g. importing real trading history, or just logging a sale a few days late with its actual fill price. `add_position`'s own docstring explicitly supports this for buys ("Creates a position from manual entry / CSV-import data"); there's no equivalent path for a historical sell. Fixing this would mean revisiting a decision the backend task already explicitly made once — needs its own `decisions` entry weighing "keep it market-price-only" against "add an optional manual exit price/date override," not just a UI tweak.

Smallest real next step: a `ClosePositionDialog` mirroring `AddPositionDialog`'s shape, at minimum wiring up the `exit_reason` selector that already has a backend home waiting for it; the exit-price/date backfill question is the harder, more debatable half and can be scoped separately.

## Letter-grade scores (A/B/C/D), not just raw grade percentages

**Read ch. 55 "Is This an A-Trade?" directly** (pp. 226–230, plus its ch. 22 cross-reference, p. 5877 of the extracted text) rather than relying on the existing paraphrase in `docs/Analyse.md` §7. It's the actual source for the buy/sell/trade grade formulas already implemented (`backend-trade-grading`) — but the chapter's own framing is explicitly a **letter grade**, not a raw number: footnote, "This term comes from the U.S. school grading system: A is excellent, B good, C mediocre, and D poor." Two concrete numeric anchors exist in the primary source:

- **≥30% of channel height captured → "A-trade"** (ch. 55's own explicit rule, already `docs/Analyse.md`'s "≥30% capture is an 'A' trade").
- **~10% captured → "C"** (ch. 22, cross-referenced from ch. 55: "capturing 10% of that channel earns you a C").

**The real gap, and why it was already deliberately left undone once:** `TradeJournalPanel.tsx` only ever renders the raw `trade_grade_pct`/`buy_grade_pct`/`sell_grade_pct` numbers (bolded above a threshold, per `docs/Analyse.md`'s ">50% very good" / "~30%+ A" anchors) — there's no A/B/C/D letter shown anywhere. Its own code comment already explains why: *"Neither full A–F letter-grade boundary is documented, so this panel deliberately shows the raw percentage... rather than inventing an unstated B/D/F cutoff."* Having now read the chapter directly and confirmed that comment's claim: **correct** — B and D have no numeric threshold anywhere in the book, only qualitative descriptions (Kerry Lovvorn, quoted in the same chapter: "if I saw no A-trades... I'd go for B-trades, and on a really slow day, reach for a C-trade") and a chart figure (55.1) that visually bands A/B/C/D on a diagram without printed percentages.

So building this for real means making an explicit, documented judgment call (a `decisions` entry, not a silent choice) on how to fill the B/D gap the book leaves open — e.g. linearly interpolating between the two known anchors (10%→C, 30%→A) and extrapolating a D-floor/A±-ceiling, versus just showing "A" and "C-or-below" and leaving B ungraded, versus something else. Only `trade_grade_pct` has book-given numeric anchors at all — buy/sell grade's only stated anchor is the single ">50% = very good" line, with no letter-grade scale attached to them in the text, so a buy/sell letter grade would need its own separate justification (or might not belong at all, staying percentage-only). Scope-wise this is a small, self-contained frontend (and maybe schema) change once that judgment call is made — the formulas and data are already there.

**Separate, bigger idea from the same chapter, not what was asked for here but worth not losing:** Elder tags every trade with a personal, named **strategy/setup type** (his own examples: "01 false breakout + bullish divergence," "pullback to value") and asks "Is this an A-trade?" *before* placing it — a pre-trade quality gate, distinct from the after-the-fact buy/sell/trade grade. Nothing in this app's schema captures a trade's strategy/setup at all today (`PositionIn`/`ClosedTradeORM` have no such field) — this would let a user eventually see which of *their own* named setups actually perform best over time, which the current per-trade-only grading can't answer. Genuinely separate scope from the letter-grade idea above.

## Market scanning (ch. 56) is a new feature, not part of the watchlist or ticker detail view

**Read ch. 56 "Scanning for Possible Trades" directly** (pp. 230–232) to check whether it belongs inside an existing page. It doesn't fit either candidate:

- **Not the ticker detail view** — that page analyzes one already-chosen ticker; a scan by definition searches tickers you *haven't* picked yet. There's no "scan" operation that makes sense for a single ticker.
- **Not the watchlist** — `app/api/routers/watchlist.py` is a small, manually-curated list of tickers, computed one at a time through the same signal engine as everything else (`_compute_signal`, `_tide_trend`). It has no bulk/broad-universe mechanism at all, and nothing about "fetch and `analyse()` one ticker" generalizes to "scan the S&P 500."

What the chapter actually describes: Elder scans a **large universe he doesn't already track** — the full S&P 500, Russell 2000, or a specific industry group (his example: all 52 gold + 14 silver stocks) — to *discover* new candidates, not to re-analyze ones he's already watching. His own tool (built with a programmer, John Bruns) is a semiautomatic MACD-divergence scanner: it doesn't wait for a completed divergence, it flags stocks that have completed the *first two legs* (parts A and B) of a potential 3-part divergence, so he can watch them for the third leg. He calls it "a watchdog that alerts you to the possibility that this market is ready to trade" — explicitly not an automatic trade-finder, just a shortlist generator he then manually reviews and prunes (from his own example: 70–80 raw hits down to 5–6 real candidates for the week). He also names concrete negative filters worth keeping in mind for any scanner: exclude illiquid names (<500k–1M avg daily volume — "more ragged" charts, worse slippage), and price-filter by direction (skip cheap stocks when scanning for shorts, expensive ones when scanning for longs).

**So the real shape of this idea is a third, new page — a Scanner/Screener — that *feeds* the watchlist rather than living inside it**, and whose per-hit drill-down is the existing ticker detail view (matching Elder's own next step: "a trader needs to work up that stock" once a scan flags it). The natural flow: run a scan → review a shortlist of candidates → `POST /api/watchlist` (`add_watchlist_item`, already built) the ones worth tracking → open each in the ticker detail view to actually work it up.

Two very different-sized ways to build the "scan a big universe" half, worth distinguishing rather than conflating:

- **Near-term, using what's already half-built**: `IBKRProvider.run_scanner` (flagged in the IBKR follow-ups idea above) exposes IBKR's own *predefined* scanner categories — 52-week-high/low, hot-by-volume, top % gainers/losers, etc. — run broker-side across their whole market universe. This is the cheap option: no new data-fetching or compute cost to this app, but it's limited to whatever categories IBKR's `/iserver/scanner/params` actually offers (confirmed not yet checked against a live gateway) — likely no way to replicate a *custom* pattern like Elder's own divergence-precursor scan.
- **The real ch. 56 idea, much bigger lift**: running this app's *own* signal engine (or a purpose-built precursor-divergence detector, distinct from the existing completed-divergence detection `app.signals` already has) across a large downloaded universe of tickers — hundreds of `get_daily_ohlcv`/`analyse()` calls per scan run. Real cost/rate-limit questions against yfinance/Stooq (this app's primary providers, not built for bulk scanning), and would need its own liquidity/price negative-filter parameters per the chapter's explicit advice. This is the feature that actually matches what Elder describes, but is a genuinely large, separate piece of work — not a quick addition to either existing page.

## Daily Homework + "Am I ready to trade?" self-test (ch. 57)

**Read ch. 57 directly** (pp. 234–238). Two genuinely separate pieces, worth scoping independently:

- **The homework spreadsheet** (17 lines): overseas markets (Far East/Europe % change), an economic calendar, currencies/commodities (Euro, Yen, Oil, Gold, Bonds — each with weekly+daily Impulse color), the Baltic Dry Index, NH-NL, VIX, S&P 500's own weekly+daily Impulse, its daily value/channel position, Force Index vs. its centerline, a daily up/down expectation (graded the next day against what actually happened), and a closing summary of how the trader plans to trade that day (actively/conservatively/defensively/day-trade/no trades). This is *broad-market* context, distinct from any single tracked ticker — closer in spirit to the personal-breadth-proxy/market-breadth ideas already logged above than to per-ticker analysis.
  - Some of this is already computable with zero new data source, by treating an index/future as an ordinary ticker through the existing pipeline: NH-NL is already the app's own "best leading indicator" per `docs/Analyse.md` (worth checking whether this app already surfaces it anywhere — if not, that's its own gap); S&P 500 weekly/daily Impulse and daily value/channel position are exactly what `analyse()` already computes for *any* ticker, so pointing it at `^GSPC`/`SPY` costs nothing new; Force Index vs. centerline is an existing indicator too. VIX (`^VIX`), Oil/Gold futures, and major currency pairs are all fetchable via yfinance the same way.
  - Genuinely unavailable from this app's current data sources: an **economic calendar** (release dates/consensus estimates — Elder's own source is Briefing.com, a third-party feed this app doesn't integrate) and the **Baltic Dry Index** (no ticker for it on yfinance/Stooq; would need a dedicated data source). These would need real new integrations, not just pointing the existing engine at a new ticker — worth flagging up front rather than discovering it mid-build.
  - The next-day expectation self-grading (did the market close where I predicted) is a tiny, self-contained record-keeping feature — write today's guess, grade it tomorrow — independent of everything else on the list.
- **The 5-question psychological readiness self-test**: purely subjective, zero market data — "how do I feel physically / how did I trade yesterday / did I do my planning / what's my mood / how busy is today," each 0/1/2, summed 0–10, color-coded (≤4 red = don't trade, 5–6 yellow = trade cautiously, 7–8 green, 9–10 yellow again — "with everything so perfect, any change is bound to be for the worse"). This is the cheapest, most self-contained piece of the whole chapter to build: a small daily form + a stored score + a color-coded banner, no market data, no provider calls, no dependency on anything else in this app. "How did I trade yesterday" could even auto-populate from yesterday's `closed_trades` realized P&L instead of asking the user to recall it by hand.

## Trade Apgar — pre-trade go/no-go scoring (ch. 58)

**Read ch. 58 directly** (pp. 238–243). This is the pre-trade counterpart to ch. 55's after-the-fact grading, and depends on the same "personal named strategy" concept flagged under the ch. 55/56 ideas above — Elder is explicit that a Trade Apgar's five questions are strategy-specific ("the scoring method you're about to see is designed for one system... All other systems will require a different test"), so this can't be built as one fixed universal form; it needs a strategy to be defined first.

His own example strategy's five questions (each scored 0/1/2, go/no-go at **≥7 total with no single zero**):
1. Weekly Impulse — Red=0, Green=1, Blue=2.
2. Daily Impulse — same scale.
3. Daily price vs. value — above value=0, in value zone=1, below value=2.
4. False breakout status — none=0, already happened=1, on the verge=2.
5. "Perfection" — neither timeframe looks perfect=0, one does=1, both do=2 (his own note: both being perfect is rare — one perfect + one merely good is fine).

**Worth noting since it changes the sizing of this idea a lot**: three of these five inputs are data this app *already computes* for any ticker, not new work — weekly/daily Impulse (`analyse()`'s existing screens output) and price-vs-value (the EMA13/EMA26 "value zone" already exposed via `channel_upper`/`channel_lower`, per the `frontend-channel-overlay` task). False-breakout status has a plausible existing hook too: `app.signals.kangaroo_tail`/`app.signals.support_resistance` already detect closely-related false-breakout-style patterns, though mapping their output onto Elder's specific none/happened/imminent 3-way scale would need its own thought, not a direct reuse. Only "perfection" is inherently subjective and has to stay a manual input. So a first version of this feature could plausibly **auto-populate 2 of 5 questions outright, semi-populate a 3rd, and leave 2 genuinely manual** — a meaningfully smaller lift than building all five from scratch, once a strategy exists to attach the Apgar to.

The rest of ch. 58's "Tradebill" (a full trade-plan form: earnings/dividend dates, entry/target/stop, dollar risk, position size, a breakeven-move price) overlaps heavily with functionality this app already has scattered across other features (earnings-date awareness per `docs/Analyse.md`, `protective_stop`, `suggest_profit_target`, the 2%/6% risk rules) — the new part isn't computing those numbers again, it's bringing them together into one pre-trade planning view gated by the Apgar score, which ties back to the still-open "no manual sell form" and "personal strategy" ideas above rather than being a clean standalone feature.

## Expanding the Trade Journal: entry notes, a two-months-later follow-up, and strategy-segmented equity curves (ch. 59)

**Read ch. 59 directly** (pp. 243–248). Checked what's already built before assuming gaps: `frontend-trade-journal`'s closed-trades table already covers a real chunk of this chapter — entry/exit dates+prices+grades (ch. 59's own "Section B") and exit reasons (Section D). In fact `app.portfolio.models.ExitReason` already matches Elder's own Section D list almost one-for-one (target hit, stop hit, reached value zone, going nowhere, starting to turn, couldn't stand the pain, recognized junk trade after entry) — the one item in the book's list not in the enum is "reaching... the envelope" as distinct from "the value zone" (the enum only has `REACHED_VALUE_ZONE`), a minor possible gap, not a missing feature.

What's genuinely not built yet:

- **Section A — why did I take this trade**: a free-text note at entry time. No field for this anywhere (`PositionIn` has no notes field). Small, self-contained addition.
- **Section E — mandatory two-months-later follow-up review**: Elder treats this as one of the journal's three core benefits, not optional — a monthly habit of reopening trades closed ~2 months ago, marking entry/exit on a current chart, and writing what hindsight shows. This app has nothing like a "trades due for follow-up review" surface at all — would need a new field (e.g. `follow_up_notes`/`follow_up_reviewed_at` on `ClosedTradeORM`) and some way to prompt "these trades from ~2 months ago are due for review," which is a genuinely new workflow, not just a form field.
- **Equity curves segmented by strategy/exit-tactic**: Elder's own example — "once you see an equity curve for exits marked 'Couldn't stand the pain,' you'll never trade without stops." This app has the raw ingredient (`closed_trades.realized_pnl` + `exit_reason` already, `strategy` once the ch. 55/56 idea lands) but no equity-curve-by-segment view anywhere — worth noting this is naturally a `dataviz`-skill chart once the underlying strategy-tagging idea exists, not before.
- Section C ("attached combination chart showing both entry and exit") is explicitly chart-annotation tooling (SnagIt, in Elder's own workflow) — flagging it as out of scope for this app rather than a real gap; a link to the ticker detail view's own chart for that date range is the realistic equivalent, not a new annotation feature.

## Broad market-breadth indicators (ch. 34–36): NH-NL, Stocks-Above-50-Day-MA, Advance/Decline

**Read ch. 34 "The New High–New Low Index," ch. 35 "Stocks above 50-Day MA," and ch. 36 "Other Stock Market Indicators" directly** (pp. 133–142). None of the three real, still-useful indicators these chapters describe are implemented — and `backend-watchlist-breadth-proxy`'s own task description already named exactly this gap explicitly: *"a cheap, no-new-data-source alternative to full market-breadth indicators (NH-NL, Advance/Decline, % stocks above 50-day MA — all of which need a broad ticker universe this app doesn't have)."* That decision built the personal-watchlist-only proxy instead precisely because these three need something this app doesn't have. This entry is the concrete elaboration of the "real market-breadth signal" idea already flagged under the IBKR follow-ups section above — worth reading together, not duplicating.

- **NH-NL (New High–New Low Index)** = daily count of stocks hitting a new 52-week high minus those hitting a new 52-week low, across NYSE+AMEX+NASDAQ. Elder calls it "the best leading indicator of the stock market." Concrete, checkable rules from the primary source:
  - **Weekly NH-NL** (5-day moving total of the daily figure): drop below **−4,000** then rally back above it → major buy signal ("a Spike," the namesake of his SpikeTrade service); rise above **+2,500** → confirms a bull market is genuinely underway (never happens in bear-market rallies, per the text).
  - **20-day NH-NL** (rolling monthly look-back instead of a full year): drop below **−500** then rally back above it → a shorter-term "Spike bounce" signal (cross-referenced to ch. 54, which this app already implements protective-stop logic from).
  - Also: level vs. centerline (above = safe to hold/add longs, below = safe to hold/add shorts), trend confirmation/non-confirmation with price, and bullish/bearish divergence against price — the same three-lens pattern (level/trend/divergence) `docs/Analyse.md` already uses for other indicators in this app, so the *framing* would be familiar even though the *data* isn't available yet.
  - **The real blocker, unchanged from the already-flagged idea**: this needs a full-market new-high/new-low count, which needs either a broad ticker universe scanned daily (expensive, the same "hardworking way" cost as the ch. 56 scanner idea) or a broker/vendor that already aggregates it — IBKR's scanner (`run_scanner`, already flagged, `/iserver/scanner/params`'s NEW_HIGH/NEW_LOW-style categories, not yet checked against a live gateway) is the most plausible near-term source, since **counting** its result-set size at a few standard scan configs would approximate NH-NL without this app fetching hundreds of tickers itself.
- **Stocks above 50-day MA** = % of all NYSE+AMEX+NASDAQ stocks trading above their own 50-day MA, plotted 0–100%. Signal is a **reversal near an extreme**, not the extreme itself: crossing above ~75% then turning down = top signal; falling to/near ~25% then turning up = bottom signal (his own note: these reference lines drift with market regime — 2013's raging bull saw buy signals fire from reversals well above 25%, so a hard-coded 25/75 cutoff would need to be treated as a starting point, not gospel). Same blocker as NH-NL: needs the same broad-universe daily scan (is this ticker above or below its own 50-day MA) that this app has no cheap way to run today.
- **Advance/Decline line** = cumulative running total of (stocks that closed up − stocks that closed down) each day, ignoring unchanged. Same trend-confirmation/divergence-vs-price reading as NH-NL, but built from simple up/down counts rather than 52-week extremes — arguably the *cheapest* of the three to approximate via a scanner (a scan for "closed up today" vs "closed down today" across a universe is a simpler category than 52-week-high/low), worth checking whether IBKR's scanner params support it before assuming it needs the same heavier lift as the other two.
- **Explicitly not worth building**: ch. 36 also lists several once-popular indicators Elder himself says are dead — TRIN, TICK, the Most Active Stocks indicator, Member/Specialist Short Sale Ratios, Odd-lot Short Sale Ratio — each killed by structural market changes (options, index arbitrage, the death of odd-lotters). Flagging these as considered-and-rejected-by-the-author-himself, not a gap to fill.

## Consensus/commitment indicators (ch. 37) — mostly already built or genuinely unavailable; CFTC data is the one real gap

**Read ch. 37 "Consensus and Commitment Indicators" directly** (pp. 142–148) before assuming this chapter is unimplemented — two of its four sub-sections turn out to already be built:

- **Legal Insider Trading** — **already implemented**: `backend-insider-transaction-clusters` (`app/signals/insider_clusters.py`) is sourced from this exact chapter (its own `decisions` entry cites "ch. 37 p. 147" for the "several insiders... within a one-month period" rule). Nothing to add here.
- **Short Interest** — **already implemented**: `short_percent_of_float` and `short_ratio` ("Days to Cover" — `backend/app/api/schemas.py` even uses that exact phrase in its field description) are both in `ExtendedData`/`DataProvider.get_extended_data`, matching this chapter's "Short Percent of Float"/"Days to Cover" pair exactly.
- **Consensus/advisory-opinion indicators** (Investors Intelligence, MarketVane, SentimenTrader — polling financial letter-writers/advisors as a contrary-opinion signal) — **genuinely unavailable**, not just unbuilt: these are paid, proprietary third-party services with no free API, unlike everything else this app sources from yfinance/Stooq/IBKR. Not a realistic near-term addition. The chapter's other contrary-opinion signals (magazine covers, clusters of same-themed newspaper ads, a spike in "pump and dump" spam) are explicitly anecdotal/manual-judgment signals, not data an API serves at all — not real software feature material.
- **Commitments of Traders (COT) reports** — the one **genuinely new, freely available** data source in this chapter: the CFTC publishes weekly long/short positioning by commercials/large speculators/small speculators for every futures market, publicly and for free (unlike the advisory-opinion services above). Elder's own framing: follow commercials (the historically successful group), fade small speculators (the historically unsuccessful group), and read current positioning against historical norms rather than an absolute level. Real scoping caveat: this is a **futures-market** indicator — this app is stock/portfolio-focused today, so COT data would be informational market-context (e.g. alongside the ch. 57 daily-homework idea's gold/oil/currency-futures lines above) rather than something that plugs into any per-stock-ticker signal the way insider clusters or short interest do.
